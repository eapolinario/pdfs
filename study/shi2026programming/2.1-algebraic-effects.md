# §2.1 — Algebraic effects

Covers §2.1 *Effects* (pp. 6–7), with the follow-up in §7.1 *Effect and Coeffect
Systems* (p. 74).

## The core idea

An **algebraic effect** splits an effectful operation into two halves:

- a **signature** — the names and types of operations a program may invoke
  (`get`, `put`, `throw`, `read_line`);
- a **handler** — the implementation, supplied later by whoever runs the program.

The program calls operations "freely," without committing to what they mean.
That decoupling is the whole point.

> **Algebraic effects.** Plotkin and Power [17, 24] showed that algebraic
> operations determine monads, establishing a framework in which effect
> interfaces are decoupled from their implementations. An effect signature Σ
> declares a set of operations (e.g., `get : () → S`, `put : S → ()` for state);
> programs invoke operations freely without committing to a particular
> interpretation.
>
> — §2.1, p. 7

And the handler form, given as Eq. (2):

> Plotkin and Pretnar [25] subsequently introduced **effect handlers**, which
> interpret operations by providing continuation semantics:
>
> ```
> handle e with { op(v, κ) ↦ … }        (2)
> ```
>
> The handler receives the operation argument `v` and the delimited continuation
> `κ`, which it may invoke zero, one, or multiple times, enabling exceptions,
> coroutines, and non-determinism within a uniform framework [26].
>
> — §2.1, p. 7

That sentence about `κ` is the load-bearing one. Everything below is it worked
out.

## Where it sits in the section

§2.1 is a three-step ladder, and reading it as a ladder helps:

1. **Effect systems** (Lucassen & Gifford [22]) — annotate the *type*:
   `Γ ⊢ t : T_effect` (Eq. 1). "This computation may do I/O."
2. **Monadic effects** (Moggi [16], Wadler [23]) — an effect *is* a value of type
   `T(A)`; `Maybe`, `State`, `IO`. The catch: `T` bakes in both interface and
   meaning, and the program must be written inside it.
3. **Algebraic effects** — keep the interface, drop the commitment to meaning.

## Worked examples

Not from the paper; these are the note's own.

### Signature

State, exactly as the paper declares it:

```
effect State {
  get : ()  → S
  put : S   → ()
}
```

A program using it is plain code — no monad, no `bind`:

```
tick() = { let n = get(); put(n + 1); n }
```

`tick` has *no idea* whether state is a mutable cell, a threaded parameter, a
log, or a mock in a test. It just names operations.

### `κ` called once — state

Interpret by threading `s` through:

```
handle tick() with {
  get((), κ) ↦ λs. κ(s)(s)          -- resume with current state
  put(s', κ) ↦ λs. κ(())(s')        -- resume, swap the state
  return(x)  ↦ λs. (x, s)
}
```

### `κ` called zero times — exceptions

Discard the continuation and the rest of the computation never runs:

```
effect Exn { throw : String → ⊥ }

handle risky() with {
  throw(msg, κ) ↦ Error(msg)        -- κ dropped ⇒ abort
  return(x)     ↦ Ok(x)
}
```

That is what `try`/`catch` is, recovered as a special case rather than a
language primitive.

### `κ` called many times — non-determinism

Resume the *same* program twice with different answers:

```
effect Choice { flip : () → Bool }

handle coins() with {
  flip((), κ) ↦ κ(true) ++ κ(false)  -- explore both worlds
  return(x)   ↦ [x]
}
```

`coins()` was written as straight-line code; the handler turned it into a
search, with no rewriting of `coins`. This is the paper's "exceptions,
coroutines, and non-determinism within a uniform framework," made concrete.

### The same program, two meanings

The modularity payoff:

```
handle fetchUser(42) with { http(req, κ) ↦ realNetwork(req, κ) }   -- production
handle fetchUser(42) with { http(req, κ) ↦ κ(cannedResponse) }     -- test
```

One `fetchUser`, two interpretations, no dependency injection plumbing.

### Familiar analogues

`async`/`await` and generators are single-use handlers hard-coded into a
language: `yield` and `await` are operations, and the event loop or `for…of`
driver is the handler holding `κ`. Algebraic effects are the generalisation —
you write your own handler.

The paper names the real implementations:

> Languages such as Koka [27, 28], Eff [29], and OCaml 5 [30] have adopted
> algebraic effects with varying design trade-offs.
>
> — §2.1, p. 7

OCaml 5's `effect` / `Effect.Deep.match_with` is the most accessible if you want
to run any of the above; Koka is closest to the paper's notation.

## Why §2.1 is there at all

Setup for a contrast, not background for its own sake. The §2 preamble says so:
these are "the key abstractions that Section 3 will operationalize as runtime
mechanisms." The contrast lands in §7.1:

> (1) In purpose, algebraic effects make effects visible to enable **modular
> interpretation**, giving one operation many handler semantics, whereas Cordis
> makes them visible to enable **tracking and reversion**, pairing every effect
> with an inverse. (2) In setting, Effekt disciplines effects **statically at the
> type level** […]; Cordis instead disciplines effects **at runtime**, aiming at
> complete resource recovery on component removal.
>
> — §7.1, p. 74

Same move (make effects visible), different goal:

| | Asks | Answer |
| --- | --- | --- |
| Algebraic effects | "Who decides what this operation *means*?" | the handler |
| Revertible effects (§3.1) | "How do I *undo* this operation?" | an inverse supplied by the caller |

Note also how little reversibility the paper demands, from the same page:

> not that the whole computation be reversible, but that each atomic effect
> admit a **one-sided inverse**, supplied by the caller at the point of
> application rather than derived, from which the inverse of any composite
> follows by composition
>
> — §7.1, p. 74

That's the sentence to carry into §3.1.

## The complaint that motivates all of it

A handler *discharges* an effect. The paper's objection to monadic effect
systems (ZIO, Effect-TS, fp-ts) is what happens afterwards:

> a requirement is discharged by interpretation, an installed service that
> supplies its operations, and when that service is withdrawn **what its
> operations performed remains in place**
>
> — §7.1, p. 74

Which is precisely the plugin-unloading problem §1.2.1 opened with.
