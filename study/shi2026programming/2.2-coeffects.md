# §2.2 — Coeffects, and what "sensitivity analysis" means

Covers §2.2 *Coeffects* (pp. 7–8) and the pivot in §2.3 (p. 8).

## The duality

Effects annotate the *type*; coeffects annotate the *context*:

```
Γ ⊢ t : T_effect      (1)   what the computation does to the world
Γ_coeffect ⊢ t : T    (3)   what the computation needs from the world
```

> Here, the context is annotated with an element of a coeffect algebra
> describing what the computation requires from its environment, such as
> resources to access, permissions to hold, or services to depend on. While
> effects model a program's impact on the world, coeffects model the world's
> constraints on the program.
>
> — §2.2, p. 7

The two flavours the section presents:

- **Comonadic coeffects** (Uustalu & Vene [32], Petricek et al. [18]) — a
  comonad `(D, ε, δ)` where `ε : D(A) → A` extracts the value from a context and
  `δ : D(A) → D(D(A))` duplicates it. The Environment comonad `D(X) = E × X` is
  dependence on a fixed environment; the Stream comonad `D(X) = ℕ → X` is
  dependence on temporal data.
- **Graded coeffects** (Brunel et al. [33], unified with graded effects by
  Gaboardi et al. [19]) — a pre-ordered semiring `𝒮 = (S, ≤, +, ×, 0, 1)` whose
  elements annotate each *variable binding*.

## Sensitivity analysis

The term appears once, in the graded-coeffects paragraph:

> The semiring operations compose coeffects sequentially (×) and in parallel
> (+), enabling precise resource tracking, **sensitivity analysis [34]**, and
> information-flow control [35, 36] within a unified algebraic framework [37].
>
> — §2.2, p. 7

Reference [34] is Reed & Pierce, *"Distance makes the types grow stronger: a
calculus for differential privacy"* (2010) — the **Fuzz** language. That fixes
the meaning: sensitivity in the **Lipschitz** sense, in service of
**differential privacy**.

### Definition

`f` is **c-sensitive** if it stretches distances by at most `c`:

```
d(f(x), f(y))  ≤  c · d(x, y)
```

Move the input one unit, the output moves at most `c`.

| Function | Sensitivity |
| --- | --- |
| `λx. 5` | 0 — output ignores `x` |
| `λx. x` | 1 — non-expansive |
| `λx. 2*x` | 2 |
| `λx. x + x` | 2 |
| `count(db)`, distance = rows differing | 1 — one row changes the count by 1 |
| `sum(ages clipped to [0,120])` | 120 — one row can swing it by 120 |
| `sum(unclipped)`, `max` | ∞ — one outlier moves it arbitrarily |

### Why it is a graded coeffect

This is the part §2.2 is actually making. Take `S = ℝ≥0 ∪ {∞}` with ordinary `+`
and `×`, and grade each binding with it:

```
Γ, x :_c A ⊢ t : B        -- "t is c-sensitive in x"
```

The paper's two composition rules are then exactly the Lipschitz arithmetic:

- **`×` (sequential)** — feeding a `c`-sensitive function into a `d`-sensitive
  one gives `c·d`. Stretches multiply along a pipeline.
- **`+` (parallel)** — if `t` uses `x` at `c` and `u` uses `x` at `d`, then
  `(t, u)` uses `x` at `c+d`. Using an input twice doubles the exposure, which
  is why `x + x` is 2-sensitive and not 1.

The paper's grade vocabulary — "0 for unused, 1 for linear use, `n` for bounded
use, ∞ for unrestricted use" — re-reads cleanly under this semiring: `0` means
the output is independent of `x`, `1` means non-expansive, `∞` means no bound.

### The payoff

Sensitivity is the missing number in the Laplace mechanism: for a `c`-sensitive
numeric query, noise drawn from `Lap(c/ε)` gives `ε`-differential privacy. Fuzz's
contribution is that **typechecking computes the noise scale** — `c` falls out of
the derivation instead of a hand-written proof per query, and a query that types
at `∞` is one you are told you cannot safely release.

## The real point of the sentence

Three unrelated analyses out of one mechanism, by swapping the semiring:

| Analysis | Semiring | A grade means |
| --- | --- | --- |
| Resource tracking | `ℕ ∪ {∞}` | times used |
| Sensitivity | `ℝ≥0 ∪ {∞}` | Lipschitz constant |
| Information flow [35, 36] | a security lattice | public / secret |

That is the "within a unified algebraic framework" claim, and it explains why
§2.2 mentions analyses Cordis never performs: it is establishing that coeffects
are a *general* discipline before §2.3 turns around and names the catch.

## The pivot in §2.3

> However, classical effect and coeffect systems are **static instruments**:
> effects are tracked within lexically fixed scopes and discharged by
> compile-time handlers; coeffect annotations are verified against contexts
> determined before execution. […] No fixed lexical scope can delimit a plugin
> loaded after deployment; no compile-time context can anticipate dependencies
> that emerge from runtime configuration.
>
> — §2.3, p. 8

Sensitivity analysis is a good illustration of the limitation, in fact: it is a
compile-time number about a fixed program, whereas the paper wants guarantees
about plugins that arrive after deployment.

§2.3 also states the correspondence the rest of the paper runs on:

- **Temporal** composability ← effects, which must admit an **inverse** so a
  component's modifications can be reverted on unload.
- **Spatial** composability ← coeffects, which are exactly inter-component
  dependencies, to be **resolved reactively** against what the environment
  supplies.

> rather than extending static type systems with more annotations, we **reify**
> the conceptual structures of effects and coeffects so that a runtime can
> operate on them directly, establishing dynamically the guarantees these
> systems provide statically.
>
> — §2.3, p. 8
