# §5.3 — Cordis in practice: versions and the shipped artifact

Covers §5.3 *Case Study: Koishi* (p. 66), specifically footnote 4.

> **Most of this note is not from the paper.** It records what the shipped
> Cordis and the DeepSeek Harness repository actually look like, gathered
> **2026-08-17** from npm and the GitHub API. Both are moving targets; treat
> every number below as a timestamped observation, not a stable fact.

## What the paper says

> Koishi currently uses Cordis **v3**. This paper presents Cordis **v4**, which
> refines the effect and coeffect semantics and redesigns the loader; the core
> compositional model is shared across both versions.
>
> — §5.3, footnote 4, p. 66

That footnote does more work than its size suggests: the empirical claims of
§5.3 are about a **v3** production system, while the formalism of §3–§5 is
**v4**. They are not the same artifact.

## The v4 timeline

npm `cordis` has 164 published versions: 1 in v0, 20 in v1, 49 in v2, 68 in v3,
26 in v4. The v4 series is the interesting one:

| Phase | Span | Releases |
| --- | --- | --- |
| Lone alpha | 2024-11-11 | `4.0.0-alpha.0` |
| *gap, ~4 months* | | |
| First burst | 2025-03-02 → 2025-06-01 | `alpha.1` … `beta.5` (14) |
| **gap, ~10 months** | 2025-06-01 → 2026-03-24 | — |
| Second burst | 2026-03-24 → 2026-08-10 | `beta.6` … `rc.8` (11) |

Commit counts on `cordiverse/cordis` (sampled, days 01–28 of each month) track
the same shape, so the quiet period was real development dormancy rather than a
pause in publishing:

```
2024-11: 34   2025-05:  4   2025-11:  0   2026-05: 13
2025-01:  0   2025-07:  2   2026-01:  0   2026-07:  7
2025-03: 52   2025-09:  1   2026-03: 31
```

**v4 has never shipped stable.** dist-tags are `latest: 4.0.0-rc.8` and
`next: 4.0.0-beta.5` — `next` still points at the pre-hiatus beta, so it is
older than `latest`. The paper therefore describes a release candidate.

## Versions are not navigable in the repo

`cordiverse/cordis` has **zero tags and zero releases** (`git ls-remote --tags`
returns nothing; `gh release list` is empty). Every version's code passed
through `main`, but no version is addressable — recovering a published version
means finding the commit that bumped `packages/core/package.json`.

Two footnotes on completeness:

- **v0.1.0 predates the repo.** Published 2022-04-21; the repo's `initial
  commit` is 2022-05-17. The tarball is 176 bytes containing only
  `package.json`, so it is a name-claiming placeholder and nothing real is
  missing.
- **The repo was renamed.** npm metadata for 1.0.0 still points at
  `github.com/shigma/cordis`, which now redirects to `cordiverse/cordis`; the
  v1/v2 history survived the move to the org.

## How the DeepSeek Harness uses Cordis

[`deepseek-ai/deepseek-harness`](https://github.com/deepseek-ai/deepseek-harness)
— created 2026-08-13, TypeScript, default branch **`master`** (not `main`),
tagline "Everything is a Plugin." It does not depend on Cordis via npm; it
**source-vendors** it.

> This directory contains source-vendored copies of the Cordis framework and its
> foundation libraries. They are copied into this monorepo instead of being
> depended on via npm, so that the harness **fully owns its framework layer
> (auditable, patchable, pinned)**.
>
> — `vendor/README.md`

Nine packages are vendored (`cordis`, `cosmokit`, `schemastery`, `loader`,
`include`, `group`, `timer`, `hmr`, `logger-console`), all rescoped into
`@deepseek-ai/*`. The rescoping has a stated reason:

> every harness package declares `cordis` as a peer dependency, so publishing
> the harness publishes this framework layer too, and a publication under the
> upstream names **would squat them on the registry**.
>
> — `vendor/README.md`

Every consumer resolves `specifier: workspace:^` to
`version: link:../../vendor/cordis` in `pnpm-lock.yaml`, with no registry copy
alongside — asserted by the repo's own `verify-vendored-links` hygiene gate.
Counting those links:

| Vendored package | Workspace packages linking it |
| --- | --- |
| `cordis` | **221** |
| `schemastery` | 219 |
| `loader` | 46 |
| `include` | 21 |
| `timer` | 7 |
| `hmr` | 4 |
| `group`, `cosmokit` | 3 each |
| `logger-console` | 1 |

Out of roughly 1,205 lockfile importers, 221 sit directly on Cordis. Usage is
the paper's machinery unmediated — `packages/core/agent-loop/src/index.ts`:

```ts
import { Context, FiberState, Service } from '@deepseek-ai/cordis'

const INACTIVE_STATES: ReadonlySet<FiberState> = new Set([
  FiberState.UNLOADING,
  FiberState.DISPOSED,

])
```

## Which v4, exactly

The vendor manifest pins provenance to upstream `cordis` **4.0.0-rc.7**, commit
`56b3d4f725681cf4556c1a8695a709cc3b6eed74`, from `cordiverse/cordis`
`packages/core`. So the harness runs the same v4 the paper formalizes.

Two divergences from that claim, though:

1. `vendor/cordis/package.json` declares version **4.0.1**, even though
   `vendor/README.md` states that "upstream version numbers are deliberately
   unchanged, so the manifest below still reads as an upstream snapshot."
2. `@deepseek-ai/cordis` is published on npm at **4.0.1** (`latest`), while
   upstream `cordis` has no stable 4.0.0 at all. DeepSeek shipped a stable
   release of its fork before upstream shipped stable.

Five of the nine manifest rows also cite `github.com/deepseek-harness/*` as
upstream, which returns 404 publicly — that provenance is not independently
checkable.

## The finding worth carrying back into §3.1

`vendor/README.md` keeps an exhaustive log of **18 local modifications**.
Number 6 patches the heart of the paper's model:

> **`cordis/src/fiber.ts` lifecycle hardening**: locally closes three
> **reentrant disposal gaps**. An effect's owner-list wrapper is registered
> before its setup body runs, so an unload begun from inside setup awaits setup
> and every collected cleanup […] Effect creation is rejected while the owner is
> `UNLOADING` (while `PENDING` and `LOADING` remain legal), **preventing
> cleanup-time registrations from escaping the unload snapshot**.
>
> — `vendor/README.md`, local modification 6

The paper's central claim is that every effect carries an inverse, so unloading
a component reverts it. This log is DeepSeek recording that the claim needed
hardening to hold under production reentrancy: an effect registered *during*
teardown escapes the unload snapshot and is never reverted. The formalism does
not obviously cover that case, and the fix is an operational rule (reject
effect creation while `UNLOADING`) rather than something falling out of the
algebra.

Modification 15 separately ports
[cordiverse/cordis#41](https://github.com/cordiverse/cordis/pull/41) (lazy
Loader config resolution), and modification 8 adds transactional
Loader/Include reconciliation with rollback — both suggesting the loader
redesign footnote 4 mentions was still settling while the paper was written.
